> Compute as a Service (CaaS) turns "give me hardware to run my stuff" into an automated, multitenant system that survives organizational growth — Google's Borg being the precursor of Kubernetes and Mesos. The software side matters as much as the infrastructure: programs must be built as cattle (stateless, failure-tolerant, service-discovery-based) to reap the benefits. And the compute choice is a high-lock-in, abstraction-level trade-off — one shared pool maximizes efficiency, but customization pressures and serverless alternatives complicate it.

## The big idea

After writing code you need hardware to run it on; renting and managing that hardware is CaaS. The chapter traces how the naive solution — SFTP the code onto a machine, SSH in, compile, run — becomes unmaintainable at scale, via Jeff Dean's 2002 complaint about running an automated data-processing task: getting a list of 50+ machines, starting a process on each, monitoring each by hand, with a human-implemented "sign-up" file to throttle usage and no automatic migration when a machine dies. Each pain point in that quote spawned a layer of automation: deployment, monitoring, healing, scheduling, and eventually bin-packing containers onto a shared fleet.

The deeper lesson is that CaaS is a *contract between two engineering organizations*: the infrastructure team automates the environment, and application teams must write software that honors the model — replaceable replicas, transient local state, no hardcoded hostnames, idempotent request handling. When both sides hold up their end, the payoff is enormous: self-healing services, batch workloads soaking up otherwise-wasted serving slack ("we run batch effectively for free"), and a single abstraction layer that absorbs machine changes so thousands of application teams don't have to.

## Section by section

### 25.1 Taming the Compute Environment

The evolution of Borg shows how each automation step answers the growth of the organization:

- **Automation of toil.** Simple automations come first: scripts to deploy binaries in parallel, exported monitoring metrics (the open-source equivalents being Grafana/Prometheus dashboards), agents that detect anomalies and kill unhealthy processes, and `while true; do run && break; done` loops — the cloud equivalent being an autohealing policy. The bigger step is **automated scheduling**: a central service knows the machine list and, on demand, picks unoccupied machines and deploys your binary — eliminating the hand-maintained sign-up file. Add machine-health scanning (e.g., mass disk read errors), automated first-line fixes (reboots, disk scans), and rescheduling work onto a new machine when one dies, and Jeff Dean's nightmare is fully automated. The result, the 2002 Global WorkQueue design document, was an early internal CaaS.
- **Containerization and multitenancy.** A one-to-one machine-to-program mapping wastes resources in several ways: job types outnumber machine types (provisioned for the largest), machines take months to arrive while programs grow (so machines are overprovisioned), and old heterogeneous machines linger. The fix: declare per-program resource requirements and let the scheduler *bin-pack* replicas. But neighbors interfere — CPU overruns cause latency blips, RAM overruns cause OOM kills or disk swap (Google universally prefers the OOM kill), dependency versions collide, `/tmp` gets fought over, and sensitive data needs protection. Hence isolation. VMs isolate well but carry a full OS's resource and boot-time overhead — wrong for batch jobs — so Borg's 2003 designers chose containers: cgroups (contributed to Linux in 2007) plus chroot jails, bind mounts, and union/overlay filesystems (Docker and LMCTFY are open-source descendants). Isolation failures are discovered over years: in 2011, Borg found the default 32,000-PID limit had become a real isolation boundary.
- **Rightsizing and autoscaling.** The 2006 Borg scheduled work from human-supplied configuration numbers — but those aren't numbers humans interact with daily, they go stale as programs grow, and stale slack ends in outages. Automating them proved "surprisingly tricky": only recently has more than half of Borg's fleet-wide resource usage been set by rightsizing automation (though that covers a larger fraction of *configurations*, freeing most engineers from sizing). This embodies "easy things should be easy, and complex things should be possible."
- **Summary.** Three growth axes — number of applications, number of copies, size of the largest application — demand ever more involved automation (GPU/TPU scheduling being a major recent Borg change). Even datacenter turnup, once a weeks-long manual specialty process, is becoming fully automated.

### 25.2 Writing Software for Managed Compute

Managed compute "took profound changes to the way we write and think about software":

- **Architecting for failure.** Processing a million documents on one machine takes 12 days; across 200 machines, 100 minutes — but the Borg scheduler may unilaterally kill and move any worker (kernel updates, bad disks, bin-packing reshuffles; "as a software author, I should neither know nor care why"). The **pets versus cattle** metaphor (attributed to Bill Baker) captures the required posture: pets get nursed back to health by panicked humans, with maintenance burden growing linearly or worse; cattle — `replica001` to `replica100` — are stamped out automatically, enabling self-healing. Cattle alone isn't enough, though: static work assignment means every lost worker wastes up to 50 minutes. Instead, split the work into 1,000 chunks of 1,000 documents, with workers reporting results and picking up the next chunk dynamically — the MapReduce (later Flume) pattern. For serving jobs, Borg signals rescheduling intent ahead of time so a container can refuse new requests and finish in-flight ones, with load balancers honoring the refusal.
- **Batch versus serving.** Batch jobs (logs analysis, ML training) run to completion and care about throughput; serving jobs run indefinitely, care about per-request latency, and have longer startup times. Serving jobs are naturally failure-resistant (requests are inherently small dynamically-assigned chunks) — *except* leaders holding system state, statically sharded data (100 servers each holding 1%; lose one, lose that slice), and servers known by hostname.
- **Managing state.** Replacing a cattle job loses all in-process and local state, so local state is transient and "real storage" lives elsewhere. The simplest rule: anything that must survive a request or a chunk goes to durable external storage; if all local state is immutable, failure resistance is nearly free. Persistent state can still be managed by cattle through state replication (3–5 replicas, consensus for writes — hard enough that Google built GFS, Bigtable, and Spanner to enable it). Local transient storage has legitimate uses: **caching** (the key lesson: "provision the cache to meet your latency goals, but provision the core application for the total load," so losing the cache layer degrades latency instead of causing an outage), warm-up data loads, and batching writes when some loss is acceptable (monitoring data), with periodic checkpointing to split long computations.
- **Connecting to a service.** A hardcoded hostname means your replicas aren't cattle. The answer is a durable service identifier resolved by a **service discovery** system the scheduler writes to; clients resolve at startup, monitor in the background, and load balancing decouples them further. Consequences: requests must sometimes be retried (even server-to-database), APIs should handle this gracefully, and mutating requests need **idempotency** — the pizza-order pattern of client-assigned identifiers, where re-submitting an existing ID just reports success. Even split-brain happens: when a "lost" machine comes back, two replicas both believe they're `replica072`; the address-resolution system disambiguates, and idempotency absorbs the duplicate work.
- **One-off code.** Engineers' analyses need compute too: skimming 1 GB of yesterday's logs works on a workstation, but 1 TB of a year's logs means a day of waiting — or minutes on a few hundred cores, "the difference between having it done in a day and not having it done at all" for iterative queries. Compute is like the markers from Chapter 1 — a thousand core-hours costs far less than a day of engineering time — but unlike markers, it's easy to grab too much by accident (one engineer left 1,000 GCE VMs running over vacation; another's debugging session spawned 8,000 workers). Quotas help; Google instead grants nearly unlimited quota for low-priority batch, which runs effectively free.

### 25.3 CaaS Over Time and Scale

- **Containers as an abstraction.** Containers began as isolation, but became an abstraction boundary between software and machine: as machines evolve, only the container layer (one team) adapts. A filesystem abstraction lets you onboard open-source software and acquisitions without custom fleet configurations or license-problematic source changes, and lets software prepackage its own dependencies — depending on machine-installed libraries is a leaky abstraction that freezes everyone on shared library versions. Containers also manage named resources: ports (Google omitted them; the result, `PickUnusedPortOrDie`, has 20,000+ usages in the C++ codebase; Docker's virtual NICs and Kubernetes pod IPs fixed this), GPUs, and accelerators.
- **Containers and implicit dependencies.** Hyrum's Law applies to the container abstraction *more* than usual — enormous user counts, and users don't even perceive the filesystem as an API. The PID story: the 32,000-PID limit could have been raised by config, except log-storage processes had come to depend on five-digit PIDs (record-name lengths broke at six digits). The fix took phases — cap PIDs per container, then split the PID space for threads versus processes (few depended on thread PIDs), and a still-unreached phase three of PID namespaces, blocked because countless systems assume `{hostname, timestamp, pid}` uniquely identifies a process; the cleanup is "still ongoing eight years later." The lesson isn't "use PID namespaces" — it's that designing a container system that stays maintainable for decades is so hard that you should prefer one developed and hardened by a broad community (Kubernetes benefited from Borg's cleanups; now, with broad adoption, it accumulates the same issues).
- **One Service to Rule Them All.** WorkQueue managed some batch jobs in one pool while each serving job had dedicated machines (the equivalent of a Kubernetes cluster per workload). In 2003 Borg assimilated everything into one pool per datacenter, for two gains. First, serving machines became cattle — the Borg design doc: "Machines are anonymous: programs don't care which machine they run on as long as it has the right characteristics" — so there aren't *n* diverging pool-management practices, just Borg, and company-wide moves (new server architecture, datacenter switches) stay feasible. Second, batch and serving needs are *complementary*: serving jobs must be overprovisioned against spikes, so their slack would otherwise idle — but batch replicas can soak up that spare 70%, being preemptible (CPU reclaimed by freezing, RAM by killing) and throughput-oriented. Depending on workload shape, either batch runs for free or serving pays only for what it uses.
- **Multitenancy for serving jobs** adds requirements: rescheduling must be throttled (losing 50% of batch replicas is a blip; losing 50% of serving replicas is an outage), and serving jobs get seconds of warning to drain in-flight requests rather than being killed without notice.
- **Submitted Configuration.** Borg receives service configuration as RPCs; managing by CLI plus tribal knowledge doesn't scale (documentation and tribal knowledge decay), and wrapping the CLI in scripts is still inferior to a **dedicated configuration language**. Services sprawl across datacenters, staging/development environments, and attached services (a memcached here, a backend there); a standardized config language expresses standard operations ("update my service to the new version of the binary, but taking down no more than 5% of capacity at any given time") and makes organization-wide tasks — swapping out every memcached, pushing a security update — tractable. It's also a prerequisite for the deployment automation of Chapter 24.

### 25.4 Choosing a Compute Service

Few organizations build their own Borg; the market spans open source (Kubernetes, Mesos; OpenWhisk and Knative at other abstraction levels) and managed offerings (EC2 autoscaling, AKS/GKE, Lambda/Cloud Functions). Two things make the choice sticky: Hyrum's Law lock-in (if your architecture lets teams treat VMs as pets, they will, and moving to cattle becomes brutal) and the surrounding ecosystem of helper tools — logging, monitoring, debugging, alerting, configuration languages, UIs — that must be rewritten on a switch. Even tiny details lock in: Borg executed user commands via `/usr/bin/bash -c $USER_COMMAND`, tried to save memory by switching to `ash`, and got alerts and a rollback — because some memory-conscious teams had replaced `bash` in their custom filesystem overlays with their own minimal executor, and now had to pay for `ash` again.

- **Centralization versus customization.** Pure centralization (one CaaS, standard tools only) is best for management overhead and resource efficiency. But diverse needs push back: Cloud's 2012 GCE VMs ran in Borg containers, yet users' VMs are pets ("my mail server is not interchangeable with your graphics rendering job"), forcing live migration support and Borg scheduling changes — a bifurcation. Search's 2011 disk-based index shards (hours to rebuild, on failure-prone spinning disks) forced Borg to let containers opt out of default disk-failure rescheduling. After 2012 the Borg team found unused features (a reminder to monitor feature usage) and power-user features that had spread via config-file copying, introducing whitelists; the API cleanup continues. The recurring question: expand the explicit (or worse, implicit) API surface for one user, or inconvenience them and keep coherence?
- **Level of abstraction: serverless.** The ladder runs from pets on bare metal, through VM offerings (IaaS up to heavier, autoscaling VMs — attractive when you need diverse operating systems or have VM-based legacy), to containers as cattle (lightweight, configurable, with holes punched for special hardware), to **serverless**: multitenant *framework servers* that dynamically load and unload teams' action code, so teams run no servers at all. Serverless is usually sold against VMs-as-pets — but the honest comparison is against persistent containers, which already deliver autoscaling and low overhead. Serverless demands truly stateless code (no Spanner inside it), sets everything up per-request, and can't scale a persistent container down to zero — whereas serverless *can*, making it cheap at the low-traffic end; at the high end, both are bounded by physical hardware. It also trades control for convenience — the Google Code Jam team ran a custom script to artificially spike traffic minutes before contest start, just to warm up enough AppEngine instances. Google's own choice: don't invest heavily in serverless — Borg already provides the benefits, Google's footprint is high-traffic, and many of its systems (GCE, BigQuery, Spanner, long-tail search) can't be stateless. For a *small* team, though, the comparison is unfair in serverless's favor: the vendor absorbs the management overhead, and a shared cluster only amortizes if it's truly shared. Prefer serverless offerings with a break-out path (Knative to Kubernetes) since you'll likely outgrow pure serverless.
- **Public versus private.** Public cloud outsources management overhead and makes scaling easier with every abstraction level — invaluable when you can't predict resource needs. The counterweight is lock-in fear (Zimki, a JavaScript PaaS, shut down in 2007 with three months' notice). Mitigations, in ascending strength: choose managed offerings built on open source architectures (a migration path exists, though Hyrum's Law guarantees some provider-specific usage); run high-level open source (Knative, OpenWhisk) on low-level cloud (EC2) so your tweaks and tooling travel with you; go multicloud (GKE plus AKS) to avoid depending on one provider's details; or run hybrid, using public cloud as overflow for a private fleet. All of these need good connectivity and common APIs between environments.

### 25.5 Conclusion

Google learned the value of a well-designed *common* compute infrastructure: one shared system (e.g., a few Kubernetes clusters per region) yields efficiency in management and resources and enables shared tooling. Containers are the key tool for both machine sharing and a durable abstraction layer. Using such an architecture well requires the cattle model — easily, automatically replaceable nodes scaling to thousands of instances, ephemeral local storage, no hardcoded hostnames. Every organization still faces a complex trade-off across pets, cattle, and serverless.

### 25.6 TL;DRs

- Scale requires a common infrastructure for running workloads in production.
- A compute solution can provide a standardized, stable abstraction and environment for software.
- Software needs to be adapted to a distributed, managed compute environment.
- The compute solution for an organization should be chosen thoughtfully to provide appropriate levels of abstraction.

## Key terms

- **Compute as a Service (CaaS)**: an automated service that provides computing power on demand — scheduling, deploying, monitoring, and healing workloads across a shared machine pool.
- **Bin-packing**: scheduling replicas onto machines by matching declared resource requirements (CPU, RAM, disk) to available capacity.
- **Pets versus cattle**: pets are individually maintained machines nursed through failures; cattle are anonymous, automatically replaced replicas — the precondition for self-healing fleets.
- **Batch job / serving job**: run-to-completion throughput-oriented programs versus indefinitely running latency-oriented programs; their needs are complementary on a shared fleet.
- **Rightsizing / autoscaling**: automation that sets (and keeps current) a workload's resource parameters instead of human-supplied configuration numbers.
- **Multitenancy**: safely sharing one machine among many tenants' workloads, requiring isolation (containers via cgroups and filesystem layering; historically VMs).
- **Service discovery**: resolving a durable service identifier to current backend addresses, written by the scheduler; usually paired with load balancing.
- **Idempotency**: guaranteeing that issuing a mutating request twice has the same effect as once — often via client-assigned identifiers.
- **State replication**: maintaining persistent data across replicas of a cattle system (with consensus for writes), so state itself survives machine loss.
- **Serverless**: running only per-request handler code on multitenant framework servers that load/unload actions dynamically; demands truly stateless code.
- **Hyrum's Law lock-in**: dependence on a compute platform's incidental behaviors (five-digit PIDs, `bash` memory footprint) that makes even trivial infra changes risky.
